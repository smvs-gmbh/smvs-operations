## Development and release workflow from this checkpoint

1. Develop locally against the local database and synthetic/local test records.
   Do not point local development or automated tests at the Jelastic database.
2. Run relevant tests, the complete suite for a release and migration checks.
   For contact deletion, verify that organisations remain and repeated imports do
   not recreate the erased contact.
3. Review changes and commit locally. Keep environment files, private keys,
   production payloads, database dumps and personalised backups out of Git.
4. Push the reviewed commit to GitHub after local acceptance. A Git push and a
   deployment are separate operations; this checkpoint introduces no automatic
   deployment pipeline.
5. Deploy an **identified commit**, not a changing working directory. Build a
   source archive using `git archive <commit>`; public Connect continues to use its
   explicit minimal file allowlist. Record commit ID, source hashes, migration
   version, time and validation in the deployment log.
6. Before deploying, check memory headroom and take database/source backups.
   Apply reviewed additive migrations first; restart only affected services and
   do not restart all processes together on a memory-constrained node.
7. Perform a small VPN/public smoke test. A real external Tally webhook and
   SendGrid delivery can be tested on Connect using a clearly marked test record
   and the approved test recipient. This is an integration smoke test, not the
   normal location for developing or debugging application logic.
8. Roll back application code to the previous identified release if needed.
   Database rollback needs its own compatibility review; do not blindly downgrade
   a schema containing live records.

The node was observed with 512 MiB RAM and exhausted swap during a previous
restart. The duplicate portal was disabled. Review Jelastic memory headroom before
another release; 2 GiB was suggested as an initial capacity target, not verified as
already provisioned.
